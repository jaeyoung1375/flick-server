# 스트리밍 도메인 로드맵 (flick-server Streaming Domain Roadmap)

> ⚠️ **이 문서의 성격: 설계 제안(계획)이지 실측 사실이 아니다.**
> `docs/ai/01~13`의 다른 문서는 "실제 코드에 있는 것"만 적는 게 원칙이지만, 이 문서는 **아직 코드에 없는 것**(콘텐츠 카탈로그·영상 인프라·구독·시청기록)을 어떤 순서로 만들지 정리한 로드맵이다. 테이블명·컬럼명·엔드포인트는 전부 **제안**이며 확정된 스펙이 아니다.
> 마일스톤이 실제로 구현되면 그 결과는 `06_domain_playbooks`(도메인 규칙)·`09_api_contract`(실제 엔드포인트)·`10_data_model`(실제 DDL)에 실측 기반으로 반영하고, 이 문서는 "진행 상황"만 갱신한다. 실제 구현 내용이 이 로드맵과 달라지면 실제 구현이 항상 우선한다.
>
> 작성 시점(2026-09-15) 기준 배경: [`flick-server-overview.md`](./flick-server-overview.md)·[`guide.md`](./guide.md) 참고. 현재 코드베이스에는 스트리밍 도메인이 전혀 없고, 인증(JWT+소셜로그인)·공통코드·메뉴·파일업로드 인프라만 남아있다.
>
> **문서 드리프트 참고:** `02_tech_stack`·`10_data_model` 등 기존 문서는 여전히 Oracle 기준으로 서술돼 있지만, 실제 코드(`build.gradle`의 `org.postgresql:postgresql` 드라이버, `File-mapper.xml`의 `nextval('CMM_FILE_SEQ')` 등)는 **이미 PostgreSQL로 전환 완료**된 상태다. 이 로드맵은 실제 코드(PostgreSQL) 기준으로 작성했다. 기존 문서의 Oracle 언급을 정정하는 것은 이번 작업 범위 밖이라 건드리지 않았다 — 별도로 갱신이 필요하다.

## 0. 왜 이 순서인가 (도메인 영역 개요와 연결 관계)

개인 포트폴리오 규모의 OTT MVP를 만든다고 할 때, 네 영역은 서로 강하게 의존한다. 의존 방향이 곧 마일스톤 순서의 근거다.

```
[콘텐츠 카탈로그]  ──(에피소드가 있어야 영상을 붙일 수 있음)──▶  [영상 인프라: 로컬 업로드→트랜스코딩→HLS]
        │                                                              │
        │ (무엇을 봤는지 기록하려면 "볼 거리"가 먼저 있어야 함)              │ (재생 가능한 스트림이 있어야 시청기록이 의미 있음)
        ▼                                                              ▼
[구독/결제] ──(재생을 구독 상태로 게이팅)──────────────────────▶ [시청기록/이어보기/추천]
```

- **콘텐츠 카탈로그**가 없으면 나머지 전부가 붙을 대상이 없다 → 항상 첫 번째.
- **영상 인프라**(로컬 디스크 업로드 → 트랜스코딩 → HLS)는 이 프로젝트에서 기술적으로 가장 리스크가 크고, 콘텐츠 카탈로그의 "에피소드" 엔티티에 종속된다 → 카탈로그 다음.
- **시청기록/이어보기**는 "재생"이라는 이벤트가 실제로 발생해야 의미가 있으므로 HLS 재생이 된 다음이어야 한다.
- **구독/결제**는 논리적으로는 시청기록보다 먼저 있어도 되지만(과금 게이트가 먼저 있는 게 실제 서비스 순서), **개인 프로젝트에서 데모 가치가 큰 "영상이 실제로 재생되는 것"을 먼저 검증**하고 나서 구독 게이팅을 얹는 편이 리스크 관리에 유리하다. 그래서 이 로드맵은 재생(M3) → 시청기록(M4) → 구독(M5) 순서로 제안한다. 결제 연동이 먼저 필요하다고 판단되면 M4/M5 순서를 바꿔도 무방하다(서로 강한 선행관계는 아님).
- **추천**은 시청기록 데이터가 쌓여야 최소한의 근거(최근 본 장르, 인기순)라도 만들 수 있으므로 가장 마지막.

## 1. 마일스톤 M1 — 콘텐츠 카탈로그 (작품/시즌/에피소드/장르/출연진)

**목표**: 영상 없이 메타데이터만으로 카탈로그 조회가 가능한 상태.

### 테이블 개요 (제안)
| 테이블 | 역할 |
|---|---|
| `CONTENT` | 작품 단위(영화 또는 시리즈). 제목·줄거리·공개연도·연령등급·포스터(`THUMBNAIL_FILE_ID` → 기존 `CMM_FILE` 재사용)·타입(`MOVIE`/`SERIES`)·공개상태 |
| `SEASON` | 시리즈의 시즌. `CONTENT_ID` FK. 영화는 시즌 없이 바로 `EPISODE` 1건으로 처리 |
| `EPISODE` | 실제 재생 단위. `CONTENT_ID`(+옵션 `SEASON_ID`) FK, 회차번호, 제목, 러닝타임. **이 시점엔 영상 컬럼 없음**(M2에서 `VIDEO_ASSET`으로 분리 연결) |
| `PERSON` | 배우/감독 등 인물. 이름·프로필사진(`CMM_FILE` 재사용) |
| `CONTENT_CAST` | `CONTENT_ID`+`PERSON_ID` 매핑. 역할구분(배우/감독/작가 등)·배역명·정렬순서 |
| (신규 테이블 없음) 장르 | 기존 `CMM_CODE`/`CMM_CODE_DTL`를 그대로 재사용(§4 참고). `CONTENT_GENRE_MAP`(`CONTENT_ID`+`DTL_CD_ID`)만 매핑 테이블로 신규 추가 |

### 핵심 API (제안)
- `GET /contents` — 목록(페이징, 장르/타입 필터) — 공개
- `GET /contents/{contentId}` — 상세(시즌·에피소드·출연진 포함) — 공개
- `POST /admin/contents`, `PUT /admin/contents/{id}`, `DELETE /admin/contents/{id}` — 관리자 CRUD
- `POST /admin/contents/{id}/episodes` — 에피소드 등록(영상 없이 메타데이터만)

### 난이도/리스크 · 개인 프로젝트 범위
난이도 낮음 — 기존 `admin/code` CRUD·`code` 공개조회 패턴을 그대로 복제하면 된다(PageHelper 페이징, MyBatis 매퍼 구조 동일). 리스크는 기술적인 것보다 **스키마 설계 결정**(시즌 없는 영화를 어떻게 다룰지, 장르를 공통코드로 갈지 별도 테이블로 갈지)에 있다 — 이 로드맵은 "영화는 SEASON 없이 EPISODE 1건", "장르는 CMM_CODE 재사용"으로 제안하되, 실제 구현 시점에 재검토 가능.

## 2. 마일스톤 M2 — 영상 업로드 → 트랜스코딩 파이프라인

**목표**: 관리자가 원본 영상을 올리면 여러 해상도의 HLS 세그먼트가 만들어져 재생 가능한 상태가 되는 것(재생 자체는 M3).

### 테이블 개요 (제안)
| 테이블 | 역할 |
|---|---|
| `VIDEO_ASSET` | `EPISODE_ID` FK(1:1). 원본 파일 경로(로컬 디스크, 예: `/app/upload/video/origin/{id}.mp4`), 트랜스코딩 상태, 러닝타임, 마스터 HLS manifest 경로 |
| `VIDEO_RENDITION` | `VIDEO_ASSET_ID` FK(1:N). 해상도(360p/480p/720p/1080p)별 비트레이트·개별 `.m3u8` 경로(로컬 디스크 하위 디렉터리) |
| (신규 테이블 없음) 상태값 | 트랜스코딩 상태(`UPLOADED`/`QUEUED`/`PROCESSING`/`COMPLETED`/`FAILED`)는 `CMM_CODE` 그룹(`VIDEO_STATUS`)으로 등록 제안 |

### 핵심 API (제안)
- `POST /admin/episodes/{episodeId}/video` — 원본 영상 파일 업로드(기존 `FileService.upload`와 동일한 멀티파트 방식, 저장 경로만 `/app/upload/video/origin/`으로 분리) → 저장 완료 시 트랜스코딩 트리거
- `GET /admin/video-assets/{id}/status` — 상태 폴링(관리자 화면에서 진행률 확인)
- (선택) `POST /internal/video-assets/{id}/transcode-callback` — 트랜스코딩 배치 스크립트가 완료 시 호출하는 콜백(비동기로 돌릴 경우)

### 난이도/리스크 · 개인 프로젝트 범위
**이 로드맵 전체에서 기술적으로 가장 어려운 구간.** 상세 설계 방향은 §3(트랜스코딩 파이프라인) 참고. 개인 프로젝트 규모 제안:
- 원본 영상은 기존 이미지 업로드와 동일하게 멀티파트로 서버 디스크에 직접 저장한다(오브젝트 스토리지·presigned URL 불필요 — §7 참고).
- 완전 자동화된 이벤트 파이프라인은 처음부터 만들지 않는다. **"업로드 완료 → 서버가 같은 서버에서 FFmpeg 트랜스코딩을 실행하고 상태를 폴링"** 수준의 반자동으로 시작해도 MVP로 충분하다.
- 여러 해상도를 전부 지원할 필요 없음 — 720p 하나만으로 "업로드→HLS 재생"이 되는 것부터 검증하고, 이후 480p/1080p를 추가하는 순서를 권장.

## 3. 마일스톤 M3 — HLS 스트리밍 재생

**목표**: 프론트엔드(HLS.js 등)가 실제로 영상을 스트리밍 재생할 수 있는 API 제공.

### 테이블 개요
신규 테이블 없음(M2의 `VIDEO_ASSET`/`VIDEO_RENDITION` 활용).

### 핵심 API (제안)
- `GET /episodes/{episodeId}/playback` — 마스터 `.m3u8` 경로 반환. 이 시점엔 로그인만 확인(구독 게이팅은 M5에서 추가)
- 정적 파일 서빙: `/app/upload/video/hls/**` 경로를 Nginx(또는 Spring `WebMvcConfigurer`의 리소스 핸들러)로 정적 서빙. `.ts` 세그먼트는 Range 요청을 지원해야 하므로 Nginx로 앞단을 두는 걸 권장(Spring 정적 리소스 핸들러도 Range를 지원하긴 하나, 실서비스 트래픽이 아니라 데모 규모에서도 Nginx가 설정이 더 간단함)

### 난이도/리스크 · 개인 프로젝트 범위
HLS.js 연동 자체는 프론트엔드 몫이라 서버 쪽 난이도는 중간. **DRM(콘텐츠 보호)·CDN은 명확히 범위 밖으로 제안** — 개인 프로젝트에서 여기까지 구현하는 건 과설계다. "아무나 URL을 긁어가서 못 보게" 하는 최소한의 보호가 필요하면, 재생 URL 발급 API에서 짧은 만료시간이 있는 서명 토큰(예: HMAC 기반 쿼리 파라미터)을 붙이는 정도만 고려하고, 이마저도 필수는 아니다.

## 4. 마일스톤 M4 — 시청기록 / 이어보기

**목표**: 로그인한 사용자의 재생 위치를 저장하고 "이어보기" 목록을 제공.

### 테이블 개요 (제안)
| 테이블 | 역할 |
|---|---|
| `WATCH_HISTORY` | `USER_ID`+`EPISODE_ID` 조합. 마지막 재생 위치(초), 시청완료여부, 갱신일시 |

### 핵심 API (제안)
- `POST /watch-history` — 재생 위치 upsert(주기적으로 프론트가 호출) — **`SecurityUtil.getUserId()` 필수**
- `GET /watch-history/continue` — 이어보기 목록(최근 갱신순)

### 난이도/리스크 · 개인 프로젝트 범위
난이도 낮음. 기존 인증 패턴 그대로 재사용. 넷플릭스식 "프로필(가구 내 다중 프로필)" 개념은 **개인 프로젝트 규모에서는 생략 제안** — `USER_ID` 1인 1계정으로 단순화하고, 여유가 있으면 이후 `PROFILE` 테이블을 얹는 확장으로 남겨둔다.

## 5. 마일스톤 M5 — 구독/결제

**목표**: 구독 상태에 따라 재생(M3)을 게이팅.

### 테이블 개요 (제안)
| 테이블 | 역할 |
|---|---|
| `SUBSCRIPTION_PLAN` | 요금제(가격, 명칭, 동시접속 허용 수 등) |
| `USER_SUBSCRIPTION` | `USER_ID`+`PLAN_ID`. 시작/종료일시, 상태(`ACTIVE`/`CANCELED`/`EXPIRED`), 자동갱신여부 |
| `PAYMENT` | `USER_SUBSCRIPTION_ID` FK. 결제수단, 상태, 결제일시 |

### 핵심 API (제안)
- `GET /subscription-plans` — 요금제 목록(공개)
- `POST /subscriptions` — 구독 시작(결제 처리 포함)
- `GET /users/me/subscription` — 내 구독 상태 조회
- M3의 `GET /episodes/{id}/playback`에 구독 상태 체크 추가(활성 구독 없으면 403)

### 난이도/리스크 · 개인 프로젝트 판단 — **실 PG 연동 대신 mock 결제 제안**
- **실제 PG(토스페이먼츠/아임포트 등) 연동은 이번 로드맵 기본안에서는 mock으로 대체할 것을 제안한다.** 이유: (1) 실 PG는 웹훅 서명검증·환불·부분취소 등 결제 도메인 자체의 복잡도가 높아 "스트리밍 서비스"라는 본래 학습 목표에서 벗어난 별도 프로젝트급 작업이 된다. (2) 개인 포트폴리오 데모에서는 "결제 UI를 누르면 구독이 활성화된다"는 흐름만 보여도 목적을 달성한다.
- mock 결제 설계: `POST /subscriptions` 호출 시 `PAYMENT.status`를 즉시 `SUCCESS`로 기록하고 `USER_SUBSCRIPTION.status = ACTIVE`로 전환. 실패 케이스(카드 거절 등)를 보여주고 싶으면 요청 파라미터에 임의의 `mockResult` 플래그를 받아 분기하는 정도로 충분.
- 확장 여지: 여유가 되면 토스페이먼츠 **테스트 모드**(실 결제 없이 API 연동 자체는 진짜로 해보는 것) 연동을 이후 과제로 남긴다 — 이건 이 로드맵의 기본 범위는 아니고 선택 확장.

## 6. 마일스톤 M6 — 추천 / 찜하기

**목표**: 최소한의 개인화.

### 테이블 개요 (제안)
| 테이블 | 역할 |
|---|---|
| `WATCHLIST` | `USER_ID`+`CONTENT_ID`. 찜한 콘텐츠(선택 기능) |

추천 자체는 별도 테이블 없이 `WATCH_HISTORY`/조회수 집계로 계산.

### 핵심 API (제안)
- `GET /recommendations` — 룰베이스(최근 시청 장르 기반 필터 또는 전체 인기순)
- `POST /watchlist/{contentId}`, `DELETE /watchlist/{contentId}`, `GET /watchlist`

### 난이도/리스크 · 개인 프로젝트 범위
**협업 필터링·ML 기반 추천은 명확히 범위 밖.** "최근 본 장르 중 하나를 골라 같은 장르 콘텐츠를 보여준다" 또는 "전체 시청기록 수 기준 인기순" 정도의 단순 룰이면 포트폴리오 목적상 충분하다.

## 7. 트랜스코딩 파이프라인 설계 방향

> **오브젝트 스토리지(S3/OCI Object Storage) 대신 로컬 디스크로 결정함(2026-09-15).** 개인 포트폴리오 규모라 CDN·다중 서버 내구성이 필요 없고, 개발 서버(OCI 인스턴스) 디스크에 그대로 저장하는 게 훨씬 단순하다. 나중에 "여러 서버로 스케일아웃" 또는 "클라우드 스토리지 연동 경험을 포트폴리오에 넣고 싶다"는 이유가 생기면, AWS S3가 아니라 **OCI Object Storage**(S3 호환 API 제공, 이미 OCI를 쓰고 있으므로)로 옮기는 걸 권장한다.

### 7.1 전체 흐름
```
[관리자 업로드]
   └─ 멀티파트로 서버(개발 서버) 디스크에 원본 저장 (/app/upload/video/origin/)
        └─ 저장 완료 → 같은 서버에서 트랜스코딩 실행 (FFmpeg 직접, 아래 참고)
             └─ 결과물(HLS 세그먼트 .ts + 화질별 .m3u8 + 마스터 .m3u8)을 로컬 디스크에 저장 (/app/upload/video/hls/)
                  └─ VIDEO_ASSET/VIDEO_RENDITION 상태를 COMPLETED로 갱신
                       └─ Nginx가 /app/upload/video/hls/** 를 정적 서빙 → M3의 재생 API가 경로 반환
```

### 7.2 트랜스코딩 실행 방식: FFmpeg 직접 실행

오브젝트 스토리지를 쓰지 않기로 했으므로, 애초에 S3 입력을 전제로 하는 AWS MediaConvert 같은 관리형 서비스는 이 구조와 맞지 않는다(관리형 트랜스코딩은 보통 오브젝트 스토리지에서 읽고 쓰는 구조라, 로컬 디스크 파이프라인에 억지로 끼워 넣으면 오히려 복잡해진다). 그래서 트랜스코딩도 서버에서 **FFmpeg를 직접 실행**하는 것으로 설계를 단순화한다.

- 업로드 완료 후 서버 프로세스(또는 별도 배치 스크립트)가 `ffmpeg` 명령으로 원본을 해상도별로 인코딩하고 HLS 세그먼트(`.ts`)와 `.m3u8`을 로컬 디스크에 직접 생성한다.
- 재시도·동시 인코딩 큐잉 같은 안정성 요소는 관리형 서비스처럼 자동으로 주어지지 않으므로 직접 만들어야 하지만, 개인 프로젝트 규모(동시에 영상 여러 개를 올릴 일이 거의 없음)에서는 "한 번에 하나씩, 실패하면 관리자가 재시도 버튼을 누른다" 수준으로 충분하다.
- **완료 알림**: 트랜스코딩을 같은 요청 스레드에서 동기로 돌리면 업로드 API가 오래 걸리므로, 별도 스레드/프로세스로 비동기 실행하고 `GET /admin/video-assets/{id}/status` 폴링으로 진행 상황을 확인하는 구조를 권장한다.
- 여유가 되면 나중에 OCI Object Storage로 옮기면서 트랜스코딩도 OCI의 관리형 미디어 서비스로 교체해보는 것도 포트폴리오 확장 여지가 있지만, 필수 확장은 아니다. 이 경우에도 "업로드/상태 관리/HLS 서빙" API 계약(§2, §3)은 그대로 유지하고 저장소 구현체만 바꾸는 방향으로 설계해두면 나중이 편하다.

### 7.3 기존 로컬 업로드 방식(`C:/upload`, `CMM_FILE`)과의 관계

- **저장 위치(로컬 디스크)는 같지만, 테이블/서비스는 분리한다.** 썸네일·포스터·프로필 사진·에디터 이미지처럼 **작고 즉시 응답 가능한 파일**은 기존 방식(`CMM_FILE` 테이블, `FileService.upload`/`uploadProfileImage` 패턴)을 그대로 재사용한다.
- **영상 원본/변환본은 디렉터리만 분리**(`/app/upload/video/` 하위)하고 `VIDEO_ASSET`/`VIDEO_RENDITION`(§2)이라는 별도 테이블로 관리한다. `CMM_FILE`을 억지로 확장해서 영상까지 담지 않는 이유:
  1. `CMM_FILE` 스키마(`FILE_ID`/`ORG_FILE_NM`/`SAVE_FILE_NM`/`FILE_PATH`/`FILE_SIZE`/`FILE_EXT`/`TEMP_YN`/`TEMP_KEY`/`DEL_YN`/`DEL_DT`, [`10_data_model`](../10_data_model/flick-server-data-model.md) 참고)에는 트랜스코딩 상태·해상도별 variant·재생시간 같은 영상 고유 속성을 넣을 자리가 없다.
  2. 이미지 업로드는 요청 하나로 즉시 끝나지만, 영상은 업로드 후 별도의 비동기 트랜스코딩 단계가 이어진다 — 처리 흐름 자체가 달라서 억지로 한 테이블/서비스에 합치면 두 책임이 섞인다.
- 콘텐츠 포스터·에피소드 썸네일은 `CONTENT`/`EPISODE`에 `THUMBNAIL_FILE_ID`(→ `CMM_FILE.FILE_ID`) FK로 연결해 기존 파일 인프라를 그대로 재사용한다.

## 8. 기존 인프라와의 연결 정리

| 기존 인프라 | 새 도메인과의 연결 방식 |
|---|---|
| JWT 인증(`SecurityUtil.getUserId()`) | 시청기록(M4)·구독(M5)·찜하기(M6) 등 **개인화 API는 전부 필수 호출**. 콘텐츠 카탈로그(M1) 공개 조회와 재생 URL 발급(M3, 로그인만 확인)은 인증 요건 수준이 다름 — 엔드포인트별로 명확히 구분해서 설계할 것 |
| `CMM_CODE`/`CMM_CODE_DTL`(공통코드) | 장르(`CONTENT_GENRE`), 연령등급, 출연진 역할구분, 트랜스코딩 상태(`VIDEO_STATUS`), 구독 상태 등 **상태값·분류값은 하드코딩 대신 공통코드 그룹으로 등록**(`harness_engineering.md` §5의 기존 관례를 그대로 따름) |
| `CMM_FILE`(파일) | 포스터·썸네일·프로필사진은 재사용(§7.3). 영상 자체는 별도 테이블(`VIDEO_ASSET`) |
| `/admin/**` 패턴 | 콘텐츠/영상 관리자 CRUD도 기존 `admin/code` 구조(컨트롤러/서비스/매퍼 분리)를 그대로 복제. 단, [`12_known_issues`](../12_known_issues/flick-server-known-issues.md) #1(role 기반 인가 없음)이 그대로 적용되므로, 관리자 화면을 실사용자에게 노출하기 전에는 이 갭을 먼저 인지할 것(이번 로드맵에서 임의로 고치지 않음) |
| PostgreSQL 채번 규칙 | 신규 테이블마다 `<TABLE>_SEQ` 시퀀스 + `<selectKey order="BEFORE"> SELECT nextval('...')` 패턴(`File-mapper.xml` 실측 패턴)을 그대로 따른다 |
